{% comment %} FILE: _includes/firebase-comments.html — Firebase-backed comments widget (Google sign-in, threaded replies, edit/delete, likes, emoji reactions, sorting, and a moderation-approval queue — all synced live via Firestore). page.comments is already checked by the parent comments.html include. Requires firebase-project-id (and the other firebase-* config keys below) to be set in _config.yml, or this include renders nothing. Styling lives in assets/css/custom-styles.css (section 35), matching the site's actual theme colors/fonts and dark-mode conventions. Moderation email notifications (comments-moderator-email / emailjs-*) are optional, if unset, new comments are still queued with approved:false but no notification email is sent; you'd need to approve them manually in the Firestore console (or via approve.html once you have a comment id). Visible comments come from two separate queries rather than one query filtered client-side: a public query (approved:true) and, for the signed-in viewer, a second query for just their own pending comments. This matches what a Firestore security rule can actually validate for a list query: a rule based on request.auth.uid == resource.data.uid (own-pending) or resource.data.approved == true (public) is provably safe, unlike trusting the client to hide unapproved comments from other viewers after a single broad read. DATA SHAPE: one Firestore document per comment in the "comments" collection, written by postComment() below with exactly these fields: text, pageUrl, uid, name, photoURL, createdAt (server time), editedAt (null until edited), deleted (false), approved (false), parentId (null for a top-level comment, else the parent's id), likes (map of uid to true), likeCount, reactions (map of emoji to a map of uid to true). The Firestore security rules (published in the Firebase console, NOT in this repository) assume this exact field list: a new comment must start unapproved with no likes or reactions and a pageUrl on the live domain; likes and reactions may only change the signed-in person's own entry; authors may edit their text only until it is approved and may delete at any time; only the moderator account may approve. If you change what this widget writes, the rules must change with it (see CLAUDE.md). SECURITY: every stored value is untrusted (any signed-in visitor can write to Firestore), so all text goes through escapeHtml() before it is put into markup. Never insert a stored value with innerHTML unescaped. PAGE MAP: the HTML below is the static shell (heading and sort menu, sign-in area, compose box, feed). The module script after it does the rest: auth, two live queries, rendering, click handling.
